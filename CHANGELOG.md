# Changelog

All notable changes to Mulchie are listed here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses
[Semantic Versioning](https://semver.org/).

## [0.3.0] - Unreleased

### Added

- `mulchie diagnose`: one prioritised picture of the machine. It covers health and why, what uses CPU and memory by app and workspace, the build queue, reclaimable space, findings, engine problems and recommendations. Each recommendation gives its reason, expected gain, risk and the next command. It changes nothing.
- Findings: Mulchie's watch reports observations about processes and about its own setup, on the scan loop. The kinds are `orphaned_process`, `missing_working_directory`, `executable_changed`, `stale_process`, `stopped_process`, `runaway_cpu`, `growing_memory`, `exposed_listener`, `temp_executable`, `hidden_dir_executable`, `system_name_mismatch`, `unsigned_executable`, `quarantined_executable`, `insecure_permissions`, `api_exposed`, `engine_lock_not_held` and `config_not_loaded`. They come from heuristics, are not malware detection, and each says why it was raised. `mulchie findings` lists them, filtered with `--severity`, `--kind` and `--all`. `mulchie findings dismiss <id>` hides one for a number of days, and `undismiss` shows it again. The settings are under `watch` in the config.
- `mulchie top` groups processes into apps (with their helper processes), agent workspaces and other programs, each with a key. `--processes` lists single processes, as before.
- `mulchie inspect <pid>`: everything known about one process, with secrets in its command line redacted.
- `mulchie signal <pid> <signal>`: signals one of your processes, and with `--tree` its descendants. It shows a plan, asks, and re-checks each process by its start time.
- `mulchie group <key> <action>`: quits, force-quits, pauses, resumes, lowers the priority of or stops the builds of an app, workspace or program as a whole, and restarts an app where the plan offers it. It shows a plan and asks first.
- `mulchie config set <key> <value>`: changes one setting. The value is JSON (a value that is not JSON is taken as a string), so it can be an object such as a budget. With an engine running the change applies at once. Out-of-range values are refused.
- MCP server: `mulchie mcp install --client claude-code|claude-desktop|cursor|codex` connects it to an agent app, `mulchie mcp uninstall` removes it, and `mulchie mcp config` prints the JSON to paste by hand. Existing config files are backed up and other entries are kept; `--dry-run` shows the change.
- MCP `--read-only` (or `MULCHIE_MCP_READ_ONLY=1`): leaves out every tool that deletes, signals, prunes or dismisses, and `check_updates`. Build slots still work.
- MCP tools: `diagnose`, `get_status`, `can_i_build`, `top_processes`, `list_workspaces`, `get_history`, `disk_breakdown`, `reclaim_candidates`, `list_findings`, `inspect_process`, `plan_cache_cleanup`, `plan_worktree_removal`, `plan_worktree_sweep`, `plan_process_action`, `execute_plan`, `prune_cache`, `dismiss_finding`, `acquire_build_slot` and `release_build_slot`, plus `list_sessions`, `get_session`, `limits_status`, `list_updates`, `check_command` and `check_updates` (see below). Each tool is marked read-only or destructive.
- Plan, then execute, everywhere. `clean`, `sweep`, `signal` and `group` show a plan and delete or signal exactly that plan after you confirm. `--dry-run` stops after the plan, `--yes` skips the question, and `--json` prints JSON. Over MCP, `execute_plan` accepts only ready items from a plan the server showed, once, within 30 minutes.
- A read-only API token (`token.read` in the config directory, printed by `mulchie token --read-only`). It is accepted for `GET` routes, the plan routes and time-limited build slots. Every other route answers 403.
- `mulchie run -- <command>`: waits for a build slot, runs the command with a fair `CARGO_BUILD_JOBS` (and `MAKEFLAGS` unless already set), and releases the slot however the command ends. It forwards SIGINT and SIGTERM and exits with the command's status. `--label` names the job in the queue. Without an engine it says so and runs the command unqueued.
- Build slots over MCP and the API are leases with a time limit (`ttl_secs`, default 900 and at most 3600 over MCP). A lease must be renewed with its ticket or it expires, so a crashed agent cannot block the queue. Releasing or renewing a ticket needs the secret returned when it was created.
- `mulchie doctor`: checks the config, token and directory permissions, the engine, git, `PATH`, the background service and how to add the MCP server. It exits 1 if any check fails.
- `mulchie service install|uninstall|status`: runs the engine at login as a launchd agent on macOS or a systemd user unit on Linux.
- `mulchie completions <shell>` for bash, zsh, fish, elvish and powershell, and `mulchie --version`.
- `mulchie token`: prints the path of the API token. The token itself is printed only with `--show`.
- Install script (`install.sh`) that verifies the tarball's SHA-256 before installing to `~/.local/bin`, and Homebrew formula and cask templates.
- Menu bar app: grouped CPU and memory usage, a "Needs attention" list of findings, process details, and an Agent API page with the connect commands.
- Menu bar app: a Sessions page with each agent session's usage and whether its limits are enforced, and Settings cards for session limits, the command guard and update checks. Each card saves only at the config revision it was drawn from.
- Linux support for the core, CLI, engine and MCP server.
- Public site with documentation, and an OpenAPI description of the local API in `docs/openapi.yaml`.
- Agent sessions: an agent and everything it started, found in the process table by name (a built-in list, extended by `agents.extra`) or registered by a hook. Per session: CPU cores, memory, processes, bytes written, runtime, build slots, listening ports and peaks. `mulchie sessions` lists them, `mulchie sessions <id>` shows one, and `mulchie sessions stop <id>` plans stopping it. `mulchie group session:<id> <action>` acts on one, and the agent's own process only with `--include-agent`. API: `GET /v1/sessions` and `GET /v1/sessions/{id}`. MCP: `list_sessions`, `get_session`, and a `session` argument on `plan_process_action`.
- Limits: budgets per session, in `limits.default` and per workspace in `limits.workspaces`, for CPU cores, memory, process count, MB written per hour and runtime. Each cap has a `sustain_secs` and an action: `notify` (the default), `deprioritize`, `pause` or `stop`. Nothing is signalled unless you set an action other than `notify`. The agent's own process is spared unless the budget sets `include_agent`. A session registered only by a hook is reported, never enforced, and only the engine that holds the engine lock acts. A pause ends after `resume_after_secs`. Every action goes through the safety gate and is journaled. A session using at least `limits.hog_share_pct` of the machine while it is strained becomes a `session_hog` finding. `mulchie limits`, `GET /v1/limits/status` and the MCP `limits_status` tool show the state. New finding kinds `limit_exceeded`, `session_hog` and `paused_list_unreadable`.
- Activity record: an append-only record per session in `<config dir>/sessions/<id>.jsonl` (mode `0600`) with session start and end, processes started, limit events and hook events. Capped per record and in total, and deleted after `sessions.retain_days` (default 14). Command lines are redacted by pattern, as well as Mulchie can, and prompt text is never stored. It is not tamper-proof: events from a hook caller other than the session's own client are stored with `unbound: true`. Read it with `mulchie sessions <id> --events`, `get_session` with `events=true` or `GET /v1/sessions/{id}/events`.
- Agent hooks: `mulchie hooks install|uninstall|status` and `mulchie hook <client> <event>` for Claude Code, Codex, Cursor, Gemini CLI and Copilot CLI. Install edits that client's user-level hook file, keeps other hooks, backs the old file up to `<file>.mulchie-backup-<unix time>`, and supports `--dry-run`. A hook fails open: with no engine, an answer later than 300 ms or any error it allows the action and exits 0. Prompt text is never sent to the engine. Codex runs new hooks only after you trust them with `/hooks`. Windsurf, Antigravity, opencode and Aider are not supported.
- Guard rules: pattern checks on shell commands, `recursive_delete`, `pipe_to_shell`, `sudo`, `force_push`, `disable_mulchie`, `credential_read` and `startup_write`, each `off`, `warn` (the default) or `block`, set under `guard.rules`. They are a tripwire on command text, not a sandbox, and miss obfuscated commands. What `warn` and `block` do depends on the client. `mulchie guard check -- <command>` and the MCP `check_command` tool ask without running anything, and `POST /v1/guard/check` is the route.
- Update checks: the engine checks the GitHub releases API for Mulchie and the npm registry for installed agent tools, and runs `brew outdated` against Homebrew's local data when the local core tap exists. Agent tool versions are read from package metadata, never by running the tool. Nothing is ever installed. Checks run at most every `updates.interval_hours` (default 24), and `updates.check off` makes no request and runs no command. Advisories for lockfile packages (`Cargo.lock`, `package-lock.json`, `go.mod`) through OSV.dev are off by default (`updates.advisories`), because they send package names and versions to a third party. `mulchie updates`, `GET /v1/updates` and the MCP tools `list_updates` and `check_updates`. New finding kinds `mulchie_update`, `agent_update`, `homebrew_outdated` and `advisory`.
- `mulchie slots` lists the build slots, and `mulchie slots release <ticket>` ends one whose holder is gone.
- `PATCH /v1/config` changes some keys with a JSON merge patch. `GET /v1/config` returns a `revision`, and `PUT` or `PATCH` with it (`If-Match` or `if_revision`) write only if nothing changed the file since, else 409 `config_changed`. A key the config does not have is refused (`unknown_key`).
- A `network` cargo feature, on by default, for the HTTPS client behind update checks. Without it (`--no-default-features`) every check reports that the build has no network support.

### Changed

- Command-line parsing uses clap: every command has `--help` with examples, flags are strict, and unknown flags are errors.
- `clean` and `sweep` no longer delete in one step. They show what they would do and, briefly, what they would skip and why.
- Worktree removal backs up first and removes only if every backup step worked. Uncommitted changes become a patch that is checked to apply cleanly, gitignored files that are not caches go into a `tar.gz`, and a detached HEAD gets a `backup/<name>-<shortsha>` branch. Each backup set is a directory under the config directory's `backups/` with a `manifest.json` that says how to restore it.
- A worktree is skipped, not removed, when it has a checked-out submodule, holds another git repository, has local edits that git hides (skip-worktree or assume-unchanged), is locked, or its HEAD moved since the plan.
- The API refuses requests with a browser `Origin` header or a `Host` other than `127.0.0.1` or `localhost`, and refuses a token file that other users can read. Each request is limited in size and time.
- Exactly one engine runs per user. The app and `mulchie serve` share a lock; the one that loses becomes a client of the other.
- The config file is checked on load and on every change. An invalid file is reported, and Mulchie runs on defaults with automatic reclaim and sweep off until it is fixed. A later save moves the invalid file aside instead of overwriting it.
- Failures to write the action journal are reported instead of dropped.

### Removed

- The MCP tools `clean_caches`, `remove_worktrees`, `sweep_worktrees`, `workspace_action` and `process_action`. Use `plan_cache_cleanup`, `plan_worktree_removal`, `plan_worktree_sweep` and `plan_process_action`, then `execute_plan`.
